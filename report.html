Abstract

This report presents resumec, a compiler written in the C programming language that translates structured plain-text resume descriptions written in a custom Domain-Specific Language (DSL) into typeset PDF documents. The system implements a complete, classical compiler pipeline: lexical analysis using GNU Flex, context-free grammar parsing using GNU Bison, Abstract Syntax Tree (AST) construction, multi-rule semantic analysis, LaTeX code generation, and PDF rendering via pdflatex.

The resume DSL supports declarations for personal information (name, email, phone, GitHub username, LinkedIn username), academic education entries with CGPA, skill lists, project entries with bullet-point descriptions, work experience entries, and arbitrary custom sections such as publications or awards. The grammar is deliberately permissive at the syntactic level — declarations may appear in any order — while enforcing structural and domain correctness at the semantic level: a missing name, an out-of-range CGPA, a malformed email address, and case-insensitive duplicate skills are all caught as semantic errors. This design allows the compiler to report multiple independent errors per run rather than halting at the first syntactic failure.

The compiler exposes a clean command-line interface with flags for controlling the output format (--tex-only, --keep-tex), CGPA scale (--cgpa-scale 4|10), and an AST inspection mode (--dump-ast). An interactive wizard mode (--interactive / -i) guides novice users through resume entry prompts, writing a .resume file and compiling it transparently.

Error diagnostics are collected centrally via a dedicated diagnostics module, sorted by source line and column, and printed in a uniform format resembling modern compiler output. LaTeX special characters in user-supplied strings are escaped before code generation, ensuring that arbitrarily typed content produces valid TeX output. The build module forks a pdflatex subprocess, moves the resulting PDF to the requested destination, and cleans up all auxiliary files.

The project demonstrates the practical application of classical compiler theory — including regular-expression-based lexical analysis, LALR(1) parsing, tree-based intermediate representation, and structured code generation — in a realistic, self-contained tool that produces tangible output. A test suite covering four negative semantic cases and a golden-file regression check validates correctness across all compiler phases.

Keywords: Compiler Design, Domain-Specific Language, Flex, Bison, Abstract Syntax Tree, Semantic Analysis, LaTeX Code Generation, PDF, C Programming, BCSE307P.

Chapter 1
Introduction
1.1 Background

Compiler design is one of the foundational disciplines of computer science, unifying ideas from formal language theory, data structures, and systems programming. A compiler maps a source language to a target language through a pipeline of well-defined phases: lexical analysis (scanning), syntactic analysis (parsing), semantic analysis, intermediate code generation, optimization, and target code generation. While production compilers such as GCC and LLVM target general-purpose programming languages, the same principles apply equally to Domain-Specific Languages (DSLs) that describe narrow problem domains.

A DSL is a small, purpose-built language whose syntax and semantics are tailored to one particular problem space, allowing users to express domain concepts directly rather than encoding them in a general-purpose language. Examples include SQL for relational queries, VHDL for hardware description, and Make for build systems. DSL compilers are an excellent vehicle for studying all compiler phases in isolation because the domain is constrained enough for the entire pipeline to fit in a small codebase while still being rich enough to exercise every phase.

1.2 Motivation

Resume creation is a universal requirement for students and professionals alike. Existing tools fall into two categories: WYSIWYG word processors (Microsoft Word, Google Docs) that require manual formatting effort and produce inconsistent output, and online builders (LinkedIn Resume, Canva) that impose rigid templates without transparency into the underlying representation.

A resume has a strongly regular structure — name, contact information, education entries, skills, projects, and experience — that maps cleanly onto a formal grammar. Treating resume construction as a compilation problem offers several concrete advantages: illegal input files are rejected with precise line/column diagnostics; multiple errors can be collected in one run; user text is escaped before being written to LaTeX, eliminating a class of encoding bugs; and the PDF layout is produced by a single deterministic code-generation pass rather than by hand-editing TeX. The approach also yields a version-control-friendly plain-text source format.

Beyond the practical output, building resumec provides an opportunity to implement every phase of a real compiler — lexer, parser, AST, semantic checker, and code generator — in a single cohesive project, directly applying the theory taught in BCSE307P (Compiler Design).

1.3 Scope of the Project

The scope of this project encompasses:

  • Design and implementation of a custom DSL grammar for resume description, supporting sections for education, skills, projects, experience, and custom sections.
  • A flex-based lexer that tokenizes the DSL, tracks source positions, and recovers from unterminated string literals.
  • A bison-based LALR(1) parser that builds an AST with error-recovery at multiple synchronization points.
  • A semantic analysis phase enforcing domain-specific rules: mandatory name, email format, phone format, CGPA range, and case-insensitive skill deduplication.
  • A LaTeX code generation phase that produces a self-contained, portable article-class document.
  • A build module that forks pdflatex to produce the final PDF and manages auxiliary files.
  • An interactive wizard mode for guided resume creation.
  • A diagnostic subsystem that collects, sorts, and prints all errors in a uniform format.
  • A test suite with positive and negative test cases.

The project does not target optimization passes, multiple target backends, or incremental compilation; its focus is on the correctness and completeness of the front-end pipeline.

Chapter 2
Project Description and Goals
2.1 Literature Review

The theoretical foundations of this project rest on the classical text Compilers: Principles, Techniques, and Tools (Aho, Lam, Sethi, Ullman, 2006 — the “Dragon Book”), which describes lexical analysis via finite automata, parsing via LR techniques, and semantic analysis via attribute grammars. GNU Flex implements scanner-generation theory converting regular-expression rules into a deterministic finite automaton. GNU Bison implements LALR(1) parsing, constructing parse tables from a context-free grammar and executing semantic actions at grammar reductions.

Domain-Specific Languages have been studied extensively in both industry and academia. Fowler (2010) in Domain-Specific Languages categorizes DSLs into internal (embedded in a host language) and external (with their own parser). resumec implements an external DSL with a dedicated lexer-parser pair, giving full control over syntax and error messages.

Existing resume-as-code solutions include JSON Resume (a JSON schema with ecosystem of renderers), Resumake (a web form filling JSON Resume), and LaTeX templates such as Jake’s Resume on Overleaf. These solutions either require users to write raw JSON/YAML (offering no domain-specific validation) or raw LaTeX (requiring typesetting expertise). None implement a full compiler pipeline with a dedicated DSL and semantic analysis. More recently, Typst (2023) brings a compiled approach to document generation, but targets a general-purpose document language rather than the narrow resume domain.

2.2 Research Gap

Despite the availability of resume-building tools and LaTeX templates, no existing lightweight open-source solution combines the following properties simultaneously:

  • A human-readable, version-control-friendly plain-text source format with a formally defined grammar.
  • A full compiler pipeline with lexer, parser, AST, and semantic analysis phases.
  • Domain-level semantic validation (CGPA range, email format, duplicate skills) with precise source-location error messages.
  • Direct PDF generation without requiring users to understand LaTeX.
  • A single self-contained C binary with no runtime dependencies beyond a LaTeX installation.

The gap is particularly significant for engineering students who need programmatic, reproducible resume generation integrated into a development workflow (e.g., as a make target alongside their project builds).

2.3 Objectives

The primary objectives of this project are:

  1. To design a minimal yet expressive DSL grammar for resume description and implement it using flex and bison.
  2. To build an AST that faithfully captures the source structure and retains line/column information for diagnostic purposes.
  3. To implement a semantic analysis phase that enforces domain rules and produces precise, user-friendly error messages.
  4. To generate well-formed, escaped LaTeX from the validated AST and render it to PDF via pdflatex.
  5. To provide a robust command-line interface and an interactive wizard mode.
  6. To validate the compiler with positive test cases (golden output matching) and negative test cases (deliberate violations, expected error messages).
2.4 Problem Statement

Design and implement a domain-specific language compiler, resumec, that reads a structured plain-text .resume file describing a person’s resume, validates it through lexical, syntactic, and semantic analysis phases, and emits a typeset PDF document. The compiler must report precise, line/column-addressed error diagnostics for all invalid inputs and must handle multiple simultaneous errors without aborting at the first failure.

Chapter 4
Design Approach and Details
4.1 System Architecture

The resumec system follows the classical linear compiler pipeline. Each phase transforms its input into a representation consumed by the next phase. The entry point src/main.c is the sole orchestrator, sequencing all phases.

All inter-phase state is carried in the Resume struct (the AST root), allocated by resume_new() and freed by resume_free() after codegen. Errors from all phases flow through src/diagnostics.c, which collects, sorts by (line, column), and prints them uniformly.

Methodology and Testing
5.1 Module Description
5.1.1 Lexer (src/lexer.l)

The lexer is specified as a flex .l file compiled to build/lexer.c at build time. It uses %option yylineno for automatic line tracking, and a manually maintained yycolumn counter reset on each newline. The YY_USER_ACTION macro fills bison’s yylloc location struct before every token action, enabling error messages to reference precise source positions.

5.1.2 Parser (src/parser.y)

The parser is a bison grammar with %define parse.error verbose, producing detailed syntax-error messages. The top-level rule resume := decl* allows declarations in any order — a deliberate design choice. This allows a file missing its name declaration to parse successfully so that semantic analysis, not the parser, reports the error. This is consistent with how all other semantic violations (bad CGPA, bad email, duplicate skill) are handled.

Error recovery is implemented at four synchronization points — decl_list, edu_entry_list, skill_list, and project_entry_list — using bison’s error token. Every recovery rule pairs yyerrok (clears error state) with yyclearin (discards current lookahead), preventing the recovery rule from firing repeatedly on the same unconsumed token and causing an infinite loop.

5.1.3 AST (src/ast.h, src/ast.c)

The AST root is the Resume struct. It contains scalar fields for five personal-information items (name, email, phone, github, linkedin), each paired with source-location fields. It also contains four dynamic arrays: EduEntry[], Skill[], Project[], ExpEntry[], plus an array of ExtraSection structs for custom sections. Each array grows by doubling capacity (amortized O(1) append). Projects and experience entries each contain a nested dynamic array of bullet strings.

5.1.4 Semantic Analysis (src/semantic.c)

The semantic_analyze() function walks the Resume tree and enforces seven rule categories via diag_error().

5.1.5 Code Generation (src/codegen.c)

codegen_write_tex() writes a self-contained LaTeX article document. The preamble uses only geometry and hyperref packages (available in BasicTeX). A custom \resumesection command draws a bold-label / rule separator for each section. User strings are passed through write_escaped() which replaces the ten TeX special characters (& % $ # _ { } ~ ^ \) with their safe equivalents.

5.1.6 PDF Build Module (src/build.c)

build_pdf() forks a child process running pdflatex -interaction=nonstopmode -halt-on-error. stdout/stderr of the child are redirected to /dev/null. If pdflatex is not on PATH, a set of macOS-specific fallback paths (Homebrew, BasicTeX, TeX Live 2024/2025) are tried via execv. On failure, the first ! line from the pdflatex log is surfaced as the error. On success, the PDF is moved to the user-specified path and all auxiliary files (.aux, .log, .out) are deleted.

5.1.7 Interactive Wizard (src/interactive.c)

When invoked with -i, run_interactive_wizard() prompts the user for each resume field in sequence with real-time regex validation — re-prompting on invalid input. It then writes the collected data as a valid .resume file to a temporary path and returns that path for the normal compiler pipeline to process.

5.1.8 Diagnostics (src/diagnostics.c)

All errors from any phase are registered via diag_error(line, col, format, ...). diag_print_all() sorts the array by (line, column) before printing. diag_has_errors() is polled by main.c after each phase to decide whether to proceed or abort.

7.3 Discussion

The most important design decision in resumec is the split between syntactic and semantic error detection. By relaxing the grammar to resume := decl*, the parser never aborts early due to a missing required field. All domain-level invariants are checked in a dedicated semantic pass. This mirrors the design of production compilers such as GCC and Clang, which defer many type and name-resolution errors to semantic phases so that the parser can recover and report multiple issues.

The error recovery mechanism in the bison grammar — pairing yyerrok with yyclearin at each synchronization point — was a subtle but critical implementation detail. Without yyclearin, a bad construct that fails to parse can cause the error rule to fire on the same lookahead token repeatedly, producing an infinite loop. This behavior is not obvious from the bison documentation and required careful analysis.

The decision to use POSIX <regex.h> for semantic validation keeps the validation code concise and the patterns self-documenting. The regex patterns for email, GitHub, and LinkedIn usernames closely mirror the actual validation rules used by those services.

The write_escaped() function in codegen.c is a defensive measure preventing user-typed content from breaking the generated LaTeX. A user who writes their email as foo_bar@example.com would, without escaping, produce foo_bar@example.com in the TeX source where _ is a LaTeX subscript command causing a pdflatex error. Escaping converts this to foo\_bar@example.com.

One known limitation is that the grammar does not support multi-line string values; all user text must fit on a single source line. A future enhancement could use a here-document syntax for long description fields. Additionally, the current code generation produces a fixed single-column layout; a future version could support multiple layout templates via a --template flag.

7.4 Cost Analysis

The total development cost of this project is zero in monetary terms. All software tools used (GCC, flex, bison, BasicTeX, bash) are free and open-source. Development was performed on student hardware (Apple MacBook with M-series chip). The estimated development effort is approximately 80–100 person-hours, distributed across: grammar design (10%), lexer/parser implementation (25%), AST and semantic analysis (20%), code generation and build module (20%), interactive wizard (10%), testing (10%), and documentation (5%).

Chapter 8
Conclusion

This project has successfully designed and implemented resumec, a complete domain-specific language compiler that transforms structured plain-text resume descriptions into typeset PDF documents. The system faithfully implements all five classical compiler phases — lexical analysis, syntactic analysis, AST construction, semantic analysis, and code generation — in a single, self-contained C codebase of approximately 1,800 lines.

The project demonstrates that formal compiler techniques are not confined to general-purpose programming languages; they apply equally well to narrow, domain-specific problems and produce software with superior error handling, reproducibility, and user experience compared to ad-hoc text-generation approaches.

Key contributions of this work include:

  • A formally specified EBNF grammar for a human-friendly resume DSL supporting six categories of resume information (personal info, education, skills, projects, experience, and custom sections).
  • An LALR(1) parser with multi-point error recovery that can report multiple syntactic errors per invocation.
  • A semantic analysis phase with seven distinct rule categories using POSIX regular expressions for format validation and producing precise source-position diagnostics.
  • A LaTeX code generation backend that safely handles arbitrary user-supplied text by escaping all TeX special characters.
  • A robust interactive wizard mode providing guided resume entry.
  • A validated test suite with golden-file regression tests and four negative-case tests.
Future Work

The following enhancements are proposed for future iterations:

  1. Multiple layout templates: Support multiple LaTeX templates (two-column, timeline, ATS-optimized) selectable via a --template CLI flag.
  2. Multi-line string support: A here-document syntax (e.g., description <<END ... END) for long descriptions.
  3. JSON/YAML export: A --json flag to emit the AST as structured data for integration with external resume ecosystems.
  4. Incremental / watch mode: A --watch mode that recompiles on source file changes, similar to latexmk.
  5. Warning vs. error distinction: Some rules could be reported as warnings rather than errors, allowing compilation to succeed while alerting the user.
  6. Windows support: Replacing POSIX fork/exec in build.c with CreateProcess for portability to Windows.

A.2 Semantic Analyzer (src/semantic.c)
#define EMAIL_PATTERN    "^[^@[:space:]]+@[^@[:space:]]+\\.[^@[:space:]]+$"
#define PHONE_PATTERN    "^[+]?[0-9 ()\\-]{6,19}$"
#define GITHUB_PATTERN   "^[A-Za-z0-9]([A-Za-z0-9-]{0,37}[A-Za-z0-9])?$"
#define LINKEDIN_PATTERN "^[A-Za-z0-9_-]{3,100}$"

void semantic_analyze(const Resume *r, double cgpa_scale) {
    /* Name required */
    if (r->name == NULL || r->name[0] == '\0')
        diag_error(1, 1, "resume must have a 'name' declaration");

    /* Email format via POSIX regex */
    if (r->email != NULL)
        check_regex(EMAIL_PATTERN, r->email, r->email_line, r->email_col,
                    "invalid email format: expected user@domain.tld");

    /* CGPA range */
    for (int i = 0; i < r->edu_count; i++) {
        double cgpa = r->edu_entries[i].cgpa;
        if (cgpa < 0.0 || cgpa > cgpa_scale)
            diag_error(r->edu_entries[i].line, r->edu_entries[i].col,
                       "CGPA %.2f out of valid range (0-%g)", cgpa, cgpa_scale);
    }

    /* Duplicate skills (case-insensitive) */
    for (int j = 0; j < r->skill_count; j++)
        for (int i = 0; i < j; i++)
            if (strcasecmp(r->skills[i].text, r->skills[j].text) == 0)
                diag_error(r->skills[j].line, r->skills[j].col,
                           "duplicate skill \"%s\"", r->skills[j].text);
}
A.3 LaTeX Escape Function (src/codegen.c)
static void write_escaped(FILE *fp, const char *text) {
    for (const char *p = text; *p; p++) {
        switch (*p) {
            case '&':  fputs("\\&", fp);               break;
            case '%':  fputs("\\%", fp);               break;
            case '$':  fputs("\\$", fp);               break;
            case '#':  fputs("\\#", fp);               break;
            case '_':  fputs("\\_", fp);               break;
            case '{':  fputs("\\{", fp);               break;
            case '}':  fputs("\\}", fp);               break;
            case '~':  fputs("\\textasciitilde{}", fp);  break;
            case '^':  fputs("\\textasciicircum{}", fp); break;
            case '\\': fputs("\\textbackslash{}", fp); break;
            default:   fputc(*p, fp);                  break;
        }
    }
}
